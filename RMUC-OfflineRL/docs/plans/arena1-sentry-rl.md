# Arena-1 哨兵决策层：规划与章程

> 状态：草案 v0.1（2026-10-28），待评审。**本文件不含代码改动。**
> 上游：`docs/adr/0001`–`0004`、`docs/plans/radar-waypoint-layer.md`、`docs/rules-2027-delta.md`。
> 术语：`GLOSSARY.md`。

## 0. 摘要

在 Arena-1 的 **2027 规则**下训练一个**哨兵本地战术策略**：1 Hz 接口、V0 每 5 s 承诺一次地读“敌方地面机器人位置与血量、双方前哨/基地血量、控制点状态、自身状态”，输出“**去哪、哪个姿态、打谁、小陀螺怎么转**”；10 Hz 的导航、云台、扳机由确定性执行器完成。

路线是“**规则基线 → BC/IQL 热启动 → 在线 RL → 消融与报告**”，总工期约 6–9 周（兼职）。它绕开了工作包最难的“雷达没有动作标签”，代价是需要一次 ADR 级别的决策主体迁移：**雷达 = 传感器/转发，哨兵 = 决策**。

### 0.1 最小闭环（2–4 周）

P0 + P1：环境封装 + 规则基线 + BC + 20 seed 评估。它不训练 RL，但能回答三件事：仿真吞吐够不够、雷达通道值不值得、规则基线有多强。这三件事不成立，P2 不必开始。**动作先按 V0 的“单意图 7 选 1”做，不碰连续航点/云台。**

## 1. 目标与非目标

### 1.1 目标

1. 一个可复现的哨兵策略（1 Hz 接口，V0 5 s 承诺），在固定阵容、固定队友池、换边多种子的协议下，控制度/胜率超过规则基线与 Arena-1 自带示例策略。
2. 一个可复用的环境封装：观测/动作/奖励/评估四件套，后续可平移到其他兵种。
3. 一份量化结论：**雷达位置输入对哨兵决策值多少控制度**（A/B/C 消融），回答“这条下行链路值不值得做”。

### 1.2 非目标

- 不承诺真车部署；真机是阶段 4 的独立决策门。
- 不做 5v5 全队多智能体；本期只学哨兵，其余四个位置是脚本。
- 不实现雷达上送、易伤翻倍、电子对抗；易伤不进入目标函数（对哨兵决策无影响）。
- 不做 2026 哨兵；Arena-1 的 2026 模式没有哨兵（`RULES_IMPLEMENTATION_AUDIT.md` 明确 7 号按步兵）。若必须 2026，另立引擎任务。
- 不把“仿真内更强”表述为“真车更强”。

## 2. 六个决策

| 编号 | 决策 | 取值 | 状态 |
|---|---|---|---|
| D1 | 赛季 | **2027**。Arena-1 只有 2027 有哨兵；`rules-2027-delta.md` 已把目标改为控制度 | 待确认 |
| D2 | 决策主体 | **哨兵本地**；雷达只转发位置。需 ADR-0005；ADR-0001 的通信方向不被违反 | 待评审 |
| D3 | 动作抽象 | **V0：5 s 承诺的单意图（7 选 1）+ 执行器**；V1 再扩姿态/目标/小陀螺 | 默认 |
| D4 | 队友 | 固定脚本池（2–3 个 Arena-1 示例策略），评估留出 | 默认 |
| D5 | 雷达输入 | **合成通道**：5 Hz、0.5–1 m 误差、100–200 ms 延迟、5–20% 丢包 | 待标定 |
| D6 | 评估 | 仿真闭环；换边、多种子、配对；不以 Elo 为判据 | 默认 |

D1 的理由：Arena-1 的 2026 模式 7 号是步兵，没有姿态、没有哨兵弹量；2027 模式有完整的全自动哨兵（400 HP / 260 热 / 30 冷却 / 100 W / 300 发 / 每分钟 100 发 / 三姿态）。2026 真实手册的姿态表与 2027 几乎一致（3 倍冷却、50% 防御、1.5 倍功率 +25% 易伤），所以 2027 哨兵可以作为 2026 的**机制代理**，但队友、地图、胜负条件都不同，是明确的 domain shift。

D2 的理由：若雷达只负责“告诉位置”，它就不需要学航点，`ADR-0003` 的“雷达没有动作日志”问题结构性消失；学习目标整个落在哨兵，而 Arena-1 的 replay 逐 tick 记录 action，标签是现成的。

## 3. I/O 规格

### 3.1 观测（约 55–60 维，Arena-1 口径）

> 真实 2027 观测不是这张表：敌方血量只能靠雷达转发，控制点没有 `progress`，基地没有 `armor_open`，坐标是官方角点帧。见 [`radar-sentry-comm-work-package.md`](radar-sentry-comm-work-package.md) §3.2.1。

| 块 | 维度 | 来源 | 说明 |
|---|---|---|---|
| 敌方地面 4 台 | 4×5 = 20 | `radar`（位置）+ 公共（血量/存活） | 相对哨兵的位置(2)、距离(1)、血量比(1)、存活(1) |
| 结构 4 座 | 4×3 = 12 | `bases` / `outposts` | 血量比、归属、装甲开合 |
| 控制点 4 个 | 4×3 = 12 | `positions` | 归属、完全/临时、占领进度；**2027 必需** |
| 自身 | 11 | `robots["7"]` | 位置(2)、血量、弹量、热量、姿态 one-hot(3)、强化余量、切换冷却、朝向 |
| 雷达状态 | 2 | wrapper | 链路 up/down、最近样本年龄 |
| 时间 | 1 | `time` | 剩余秒 / 420 |

- 最小版（只按“敌方位置+血量、结构血量”）：约 35 维；控制点与自身状态必须保留，否则“去哪/用什么姿态”没有依据。
- 归一化：场地 28×15 → `[-1,1]`；血量/弹量/热量比值；角度用 `sin/cos`。
- 不喂：不可见敌方的位置、任何 `snapshot()` 全量状态。队友位置可选：2027 协议 0x020B 以 1 Hz 把己方重装/3/4 的位置发给哨兵，属于裁判链路，不是多机通信；真实 schema 见通信工作包。

### 3.2 动作（V1 备选：多通道，V0 之后再做）

> 先做 §3.4 的 V0；下表是 V1，等 V0 跑通、确认宏集合是瓶颈后再拆通道。

| 通道 | 类型 | 取值 | 执行 |
|---|---|---|---|
| 去哪 | 离散 K=12–16（或连续 2 维） | 8 张增益卡、补给区、制高点、通道口、当前点 | 1 Hz 选点；10 Hz `sdk.navigate` → `move` |
| 姿态 | 3 类 | `attack` / `defense` / `move` | `posture`；5 s 冷却由引擎强制 |
| 强化 | 2 类 | on / off | `posture_enhanced`；15 s 预算 |
| 打谁 | 5 类 | 4 台地面敌 + 无目标 | `sdk.aim_at` / `aim_pitch`；`can_fire` 时 `fire` |
| 小陀螺 | 3 类 | 停 / 正 / 反 | `yaw_rate`，受扭矩与惯量限制 |
| 买弹/复活 | 规则 | 不学 | wrapper 按阈值触发（弹药 < 20% 且脱战、死亡且金币够） |

- 小陀螺与瞄准解耦：`yaw_rate` 只改底盘朝向，`aim` 是世界云台角，引擎解算；云台跟不上时由 wrapper 限制组合。
- 动作保持到下一次决策；姿态冷却与强化预算由引擎校验，策略输出非法值只记 `invalid_action`，不崩。

### 3.3 频率

| 项 | 值 | 说明 |
|---|---|---|
| 决策 | 1 Hz 接口 / V0 5 s 承诺 | V0 每 5 s 重选一次，84 步/局；V1 可回到 1 Hz |
| 执行 | 10 Hz | 导航/云台/扳机 |
| 物理 | 20 Hz | 引擎 0.05 s/步；V0 每决策 100 步，V1 每决策 20 步 |
| 雷达 | 5 Hz | 合成通道；下行节奏受多机通信上限约束，待核实 |
| 姿态冷却 | 5 s | 规则 |
| 强化预算 | 15 s/姿态 | 规则 |
| 单局 | 420 s（训练可 180–240 s） | V0 约 84 次决策；V1 420 次（10 Hz 执行 4200 次） |

### 3.4 V0：单意图（推荐先做）

把动作简化成 **7 选 1**：策略每个决策点（V0 每 5 s）只说“现在干什么”，走位、云台、扳机、小陀螺由执行器按意图完成。这是宏动作/选项（option）形式，学习问题从“连续控制”变成“小规模离散决策”。

| 意图 | 目标点 | 姿态 | 目标 | 小陀螺 | 可用条件（掩码） |
|---|---|---|---|---|---|
| `HOLD_OUTPOST` 守前哨 | 己方前哨卡 / 中央高地卡（优先空卡） | 受击或低血 `defense`，否则 `attack` | 12 m 内最近可见敌 | 受击或敌 < 6 m | 默认 |
| `HOLD_BASE` 守基地 | 己方基地卡 / 堡垒卡 | `defense` | 同上 | 同上 | 己方前哨被夺或基地被开 |
| `TAKE_OUTPOST` 抢前哨 | 敌方前哨卡 / 中央高地卡 | 途中 `move`，上卡 `attack` | 同上 | 移动时开 | 己方前哨完全控制且无敌方占领进度 |
| `TAKE_BASE` 开基地 | 敌方堡垒卡 | `attack` | 同上 | 上卡后开 | 180 s 后且己方控制敌方前哨 |
| `RESUPPLY` 补给 | 己方补给区 | `move` | 不主动交战 | 开 | 弹药 < 30% 或 HP < 60% |
| `ENGAGE` 交战 | 最近可见敌（保持 6–10 m） | `attack` | 该敌 | 敌 < 6 m 开 | 有可见敌 |
| `RETREAT` 撤退 | 己方基地 / 补给区 | `defense` | 不主动 | 开 | HP < 35% |

- 执行器共用：`sdk.navigate` 到目标点；`sdk.aim_at` 选中目标；`sdk.can_fire` 时开火；`yaw_rate` 按表；`RESUPPLY` 时买弹/回血。
- 承诺：每个意图至少 5 s（与占点 5 s 对齐），训练时按 `action repeat=5` 处理；正在占点且进度 > 0 时延长到占领完成/被打断；HP < 20% 或己方阵地丢失可提前打断。
- 掩码：上表的“可用条件”不满足时屏蔽该意图，减少无效动作；姿态冷却、热量、弹药、越界仍由执行器与引擎兜住。
- 为什么更容易：动作只有 7 个、没有连续回归；每个意图的预期效果清楚，信用分配容易；执行器兜住安全/热量/弹药；BC 标签只需判断“脚本这 5 s 最像哪个意图”；PPO 在 7 个动作上样本效率高；输出一个整数，车端/BT 可直接消费。
- 代价：精细走位、目标切换、小陀螺时机被执行器固定；宏集合就是上限。V1 再把姿态/目标/小陀螺拆成独立头，或扩宏（例如“卡掩体”“拉扯”）。

## 4. 环境封装

### 4.1 进程与节拍

直接驱动 `rmuc_arena.engine.Match`，不走 Docker、不走策略子进程：

```python
from rmuc_arena.engine import Match
from rmuc_arena.models import mirrored_lineups

lineups = mirrored_lineups({"1":2711,"3":2731,"4":2732,"6":2761,"7":2771}, "2027")
env = Match(seed=seed, duration=420, map_name="rmuc2027", lineups=lineups)
obs = env.observation("red", [7])             # 受限观测
frame = env.step(commands)                    # 0.05 s/步；V0 每 100 步一次决策
```

- V0 每个 5 s 决策周期 100 个引擎步（V1 1 Hz 时 20 步）；执行器每 2 步（10 Hz）把同一个宏目标换算成当前指令。
- 队友：红方 1/3/4/6 与蓝方 5 个槽位都要有指令，否则对应机器人停住。优先用 Arena-1 的 team 策略驱动并**丢弃它对 7 号的输出**；若该策略依赖 7 号的受控状态而产生错位，改用规则队友或单机策略。评估时换成留出的示例策略。
- 并行：每局一个进程/引擎子进程；32 核可并行 8–16 局，无向量化。
- 前置：Rust 工具链 + `cargo build --release --manifest-path simulation/Cargo.toml`（引擎指纹会校验规则哈希）。本机当前没有 cargo、torch、GPU 驱动，P0 第一件事是装工具链并实测单局耗时。
- 依赖：把 `Arena-1/` 加入 `sys.path`（或 `pip install -e Arena-1`）；引擎二进制按 `RMUC_SIM_BINARY` 或默认 `simulation/target/release/rmuc-sim` 加载。

主循环的节拍：

```python
for step in range(84):                        # V0：5 s 承诺 → 84 步/局
    obs = build_obs(env, radar)               # 受限观测 + 合成雷达
    a = policy(obs)                           # 7 选 1：现在干什么
    for k in range(100):                      # 100 × 0.05 s = 5 s
        cmd = executor(a, k // 2)             # 每 2 步更新一次（10 Hz）
        frame = env.step({"red": {"7": cmd}, "blue": blue_cmd(k)})
    r, done = reward(frame, 5)                # 5 s 累计奖励
```

### 4.2 观测构造与防泄漏

`obs_policy = observation("red", [7])` + 合成 `radar`：

- 雷达样本从 `snapshot()` 的 ground truth 生成：只取**敌方地面**机器人；5 Hz 采样；加高斯误差（0.5–1 m）；加 100–200 ms 延迟；按概率丢包；带 `age` 与 `link`。
- 结构血量、控制点、敌方兵种/血量/存活本来就是公共字段，直接取。
- **禁止**把 `snapshot()` 全量或未加噪的敌方位置传给策略；A/B/C 消融里的 C 组只做上界，不参与训练。
- 单元测试：同一 seed、同一动作序列两次运行，digest 与最终控制度一致；把 `radar` 关掉后策略输入维度不变、性能下降（证明没有暗泄漏）。

### 4.3 奖励

```
R = w1·Δ控制度（队级）
  + w2·结构伤害（前哨/基地）
  + w3·存活与受击（单位时间受击伤害为负）
  + w4·弹药效率（命中/发弹）
  + Φ(s') − Φ(s)          # potential-based shaping，Φ = 占点进度 + 位置价值
```

- 塑形只用 potential-based；受击/超温是成本项，不是塑形。硬约束（越界、超温、无弹）用终止/掩码处理。
- 控制度是队级量，哨兵单独推不动 +1/+3：先记录“哨兵在卡上”的指示量，用差值奖励/反事实归属做第二阶段；第一期允许 team-level 奖励 + shaping。
- 小陀螺的收益来自受击分布；若 `w3` 不体现“减少受击”，策略会忽略它——先把 `w3` 设成显式项，再做消融。

### 4.4 终止、日志、确定性

- 终止：420 s 或任一方基地被毁；训练可截断到 180–240 s。
- 日志：每决策记录 obs/action/reward/控制度/事件；评估局保存 replay v4。
- 确定性：Rapier `enhanced-determinism`；同 seed + 同动作序列应可复现；规则哈希随 replay 保存。

## 5. 数据与训练

### 5.1 阶段 1：规则基线（不训练）

手写一个 2027 哨兵策略：默认守己方前哨卡、控制点被夺时转防、血量低切防御姿态、热量高切攻击/停火、按最近可见敌选目标、被集火时小陀螺。作用：sanity check、数据源、RL 的下限基线。

### 5.2 阶段 2：BC/IQL 热启动

- 数据：3–4 个 Arena-1 示例策略各跑 50–100 局；每局约 84 条 `(obs, action)`（5 s 决策步长）；动作标签直接取 replay 的 `actions[team]["7"]` 在对应 5 s 窗口内的行为。总量约 1.3–3.4 万条。
- 标签口径（V0）：意图 = 脚本这 5 s 的行为与哪个宏最接近（目标点距离、是否在交火、是否在补给）；V1 才需要“去哪/姿态/打谁/小陀螺”的细标签。
- 复用：`rm_rl` 的 IQL/BC/DT 训练循环；新增特征构造器。V0 只在现有 10 维动作上加一个 7 类意图头；V1 再扩到 18 维（姿态 3 + 强化 2 + 小陀螺 3）。
- 验收：BC 的意图分类准确率/混淆矩阵显著优于随机；无策略错误；作为 PPO 的初始化。
- 预期：BC 的上限就是示例策略。PPO 若超不过它，结论是“在仿真里规则策略已足够”，这也是有价值的结果，不要为了“RL 更强”而调参。

### 5.3 阶段 3：在线 RL

- 算法：V0 用 7 类离散 PPO（或 DQN）；V1 再做混合动作（离散选点/姿态/目标/小陀螺，连续可选）；V0 5 s 决策；奖励如 §4.3。
- 队友池：3 个示例策略轮换；评估用留出的第 4 个。
- 课程：先 180 s、固定队友；再 420 s、轮换队友。
- 规模：先 0.2M–0.5M 决策（约 2.4k–6k 局）；32 核、无 GPU，按单局 30–60 s 估，数小时一轮。

### 5.4 阶段 4（可选）：对手池/自博弈

若 PPO 稳定超过基线，再加入历史 checkpoint 与镜像对手；本期不承诺。

### 5.5 V0 的 RL 构建

**MDP**

| 项 | 定义 |
|---|---|
| 状态 | §3.1 的约 58 维；可选堆 3 帧（15 s 历史），或给每台敌加 2 维雷达差分速度 |
| 动作 | 7 类意图；带掩码的 categorical |
| 决策步长 | 5 s（`action repeat=5`），84 步/局 |
| 转移 | 执行器跑 100 个 0.05 s 引擎步 |
| 奖励 | 5 s 累计，见下 |
| 折扣 | γ=0.99/步（约 500 s 有效时域），GAE λ=0.95 |
| 终止 | 420 s 或任一方基地被毁 |

**掩码**（每个决策点重算）

| 意图 | 可用条件 |
|---|---|
| `HOLD_OUTPOST` | 永远可用（全掩码时的 fallback） |
| `HOLD_BASE` | 己方前哨非完全控制，或基地装甲已开 |
| `TAKE_OUTPOST` | 己方前哨完全控制且无敌方占领进度 |
| `TAKE_BASE` | t ≥ 180 s 且己方控制敌方前哨 |
| `RESUPPLY` | 弹药 < 30% 或 HP < 60% |
| `ENGAGE` | 15 m 内有可见敌 |
| `RETREAT` | HP < 35% 且 10 m 内有敌 |

**奖励**（5 s 累计，初始权重）

```
r = 1.00·Δ控制度
  + 0.001·结构伤害
  + 0.01·(造成伤害 − 承受伤害)
  + 0.05·命中数
  + [Φ(s') − Φ(s)]，Φ = 5·Σ占点进度 + 0.5·(1 − 到当前目标卡距离/20)
  + 终局：胜 +10 / 负 −10；基地被毁 ±5
```

- 训练时用 running mean/std 归一化，clip ±10；权重写进 config，做消融。
- 控制度是队级量：先记录“哨兵在卡上”的指示量，第二阶段再做差值/反事实归属。

**算法**

1. **BC 预训练**：7 类交叉熵，类别权重（`HOLD_OUTPOST` 会占多数），30 epoch，label smoothing 0.05；保存 `bc.pt`。
2. **PPO**：masked categorical；16 个并行 env；每 env 84 步；batch 4096；4 epoch；lr 3e-4；clip 0.2；entropy 0.01；value coef 0.5；max grad 0.5；0.2M–0.5M 步。
3. 可选：加 KL anchor 到 BC（β=0.1），防止策略塌到“一直守点”。
4. 不引入 SB3/Gym；写一个 CleanRL 风格的 PPO（约 300 行，torch），env 用自定义 `step_macro()`。

**标签器（BC 用）**

对每个 5 s 窗口，取脚本哨兵的平均位置、是否发弹、血量/弹药：

| 条件 | 标签 |
|---|---|
| 距己方补给 < 2 m 且（弹药 < 30% 或 HP < 60%） | `RESUPPLY` |
| 距己方前哨卡/中央高地卡 < 2 m | `HOLD_OUTPOST` |
| 距己方基地卡/堡垒卡 < 2 m | `HOLD_BASE` |
| 距敌方前哨卡/中央高地卡 < 2 m | `TAKE_OUTPOST` |
| 距敌方堡垒卡 < 2 m | `TAKE_BASE` |
| HP < 35% 且朝己方基地/补给移动 | `RETREAT` |
| 5 s 内发弹 > 阈值且 12 m 内有敌 | `ENGAGE` |
| 其余 | 最近目标点对应的宏 |

- 先看标签分布与混淆矩阵；`HOLD_OUTPOST` 过多时用类别权重/平衡采样。
- 可选 DAgger：用 BC 策略跑，遇到不确定状态再用标签器标注，补进数据集。

**训练循环**

```python
obs = [env.reset() for env in envs]                 # 16 个 worker
for update in range(updates):
    rollouts = []
    for t in range(84):                             # 一局 84 步
        masks = [action_mask(o) for o in obs]
        acts, logps, values = policy(obs, masks)    # masked categorical
        next_obs, rewards, dones = [], [], []
        for env, o, a, logp, v in zip(envs, obs, acts, logps, values):
            o2, r, d = env.step_macro(a)            # 5 s，100 个引擎步
            next_obs.append(o2); rewards.append(r); dones.append(d)
            rollouts.append((o, a, r, o2, d, logp, v, masks))
        obs = [o2 if not d else env.reset()
               for env, o2, d in zip(envs, next_obs, dones)]
    ppo_update(rollouts, gamma=0.99, lam=0.95)
```

- `env.step_macro(a)`：执行器按宏跑 5 s，累计奖励，返回下一个观测；`done` 时重开。
- 评估：argmax 动作，20–30 个 seed，红蓝换边，留出队友；对比规则基线/BC/PPO。

**构建顺序**（不含 P0 环境封装，P0 另计 1–2 周）

| 步骤 | 交付 | 验收 | 估计 |
|---|---|---|---|
| 1 | 执行器 + 规则策略（不训练） | 7 个意图都能跑；基线控制度可复现 | 3–5 天 |
| 2 | 日志 + 标签器 + BC | 分类准确率/混淆矩阵可信 | 1 周 |
| 3 | PPO | 换边 20 seed 上 > 规则基线 | 1–2 周 |
| 4 | 消融/报告 | A/B/C + 意图集 + 决策周期 | 1 周 |

**坑**

- 5 s 承诺意味着最多 5 s 不改变宏；执行器必须在宏内处理紧急情况（HP < 20%、阵地丢失、目标死亡），否则会被打穿。
- PPO 容易塌到 `HOLD_OUTPOST`（安全、常可用）；用 entropy、类别权重、动作分布监控。
- 掩码写错会让某个意图永远不可用；每个条件写单测，记录掩码率。
- 队级奖励会奖励队友的贡献；先记录“哨兵在卡上”，再考虑差值奖励。
- 标签器是启发式，BC 的上限是标签器 + 示例策略；先看混淆矩阵再调网络。
- 评估 seed 必须与训练 seed 分离，否则结论不可信。

## 6. 评估与消融

### 6.1 协议

- 固定阵容（2711 / 2731 / 2732 / 2761 / 2771），红蓝换边，20–30 个 seed，配对比较。
- 指标：控制度、胜率、前哨/基地伤害、存活时长、发弹/命中、姿态使用分布、小陀螺占比。
- 基线：规则基线、Arena-1 示例策略、BC、PPO。
- 统计：均值 ± 95% CI；配对差值；不报 Elo。

### 6.2 消融

| 消融 | 目的 |
|---|---|
| A：仅自身视觉 / B：+合成雷达 / C：神谕位置 | 雷达位置输入的边际价值（B−A），完美信息上界（C−B） |
| 姿态开/关（V1） | 姿态决策的贡献 |
| 小陀螺开/关（V1） | 受击规避的贡献 |
| 5 s / 1 Hz 决策周期 | 承诺长度 vs 反应速度 |
| 意图集 5 / 7 / 9 | 宏集合是否够用 |
| 奖励 shaping 开/关 | 是否只是 shaping 在起作用 |
| 队友池 1 / 3 | 过拟合队友的程度 |

## 7. 阶段、验收、工期

| 阶段 | 交付 | 验收 | 估计 |
|---|---|---|---|
| P0 环境与规格 | wrapper、obs/action 规格、吞吐与确定性报告 | 同 seed 可复现；单局耗时与 steps/s 有数；无泄漏测试通过 | 1–2 周 |

## 8. Kill criteria

- P0：单局 > 60 s，或观测无法遮蔽（暗泄漏），或引擎无法稳定复现 → 降级为“只做评估器”，不进入 RL。
- P1：BC 连规则基线都显著不如 → 先查特征/标签，不急着上 PPO。
- P2：PPO 在 0.5M 决策后仍无增益 → 改用 IQL/DT 或退回规则占点规划。
- P3：B−A 小于噪声 → 砍掉雷达通道，保留自身视觉版本，节省工程量。

## 9. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 2026/2027 分叉 | 若必须 2026，Arena-1 无哨兵 | 先确认 D1；2026 需另立引擎任务（roster/型号/检录/测试） |
| 控制度是队级量 | 哨兵信用分配难 | 记录“在卡上”指示；差值奖励/反事实归属；必要时改用局部 shaping |
| 队友过拟合 | 换队友即退化 | 队友池 + 留出评估 + 随机化 |
| 雷达噪声模型无规则依据 | 训练/真车不一致 | 0.3/0.8/1.5 m、5/2 Hz、10%/30% 丢包做敏感性分析 |
| Arena-1 beta | 规则/物理变动 | 锁版本 + 规则哈希；每轮评估记录版本 |
| 仿真到真车 | 感知/动力学/接口差异 | 阶段 4 门；真车日志校准；不在本期承诺 |
| 算力 | 32 核/14 GB/无 GPU | 小模型 + 短课程；自博弈规模受限 |
| 84 步时域（5 s） | 稀疏奖励难训 | shaping + 课程；先短局 |
| 小陀螺收益隐式 | 策略学不到 | 显式受击惩罚 + 开关消融 |
| 奖励投机 | 卡点刷伤害/刷占点 | 控制度为主、结构伤害封顶、换边多种子、行为可视化 |

## 11. 待确认

1. **2026 还是 2027？** 这决定是“直接开跑”还是“先补 2026 哨兵”。
2. **哨兵跑自动还是半自动？** Arena-1 没有指挥手，半自动不可用；若真车是半自动，策略定位要改。
3. **雷达下行的噪声/延迟/丢包**由谁标定？规则只给了上送准确度阈值，没给下行测量模型。
4. **队友池选哪几个示例策略？** 评估留出哪一个？
5. **真车算力与接口**：能否 1 Hz 接收雷达位置、跑小模型、接行为树/仲裁层？
6. **是否接受 ADR-0005**（决策主体迁移）？不接受则本规划退化为“Arena-1 只做评估器”。
